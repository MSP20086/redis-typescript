Without pipelining, each request costs a full loopback round trip (two syscalls on each side), and that caps *both* servers at a similar rate on this machine. Real Redis gains only about 8% even when `redis-benchmark` runs with 4 threads. The differences that show up here are in the tail (p99), where V8 garbage-collection pauses and the JS event loop add jitter that C Redis doesn't have, and in commands that build large replies (`LRANGE_100`). Section 2 removes the round-trip limit and shows how much work each server does per command.

`LPUSH` is the outlier among the writes. `redis-benchmark` pushes every element onto one key, and lists are stored as JS arrays, so `LPUSH` (`Array.prototype.unshift`) is O(n) and slows down as the list grows. `RPUSH` (`push`) is amortised O(1) and stays close to Redis. A deque would fix this; Redis uses quicklists for the same reason.

## 5. Durability: AOF fsync policy

50 clients, `SET` only. `everysec` appends to the file on every write but calls `fsync` from a 1-second timer, so a crash loses at most about a second of writes and costs little throughput. `always` calls `fsync` before replying to each write. That makes every write durable, but each one now waits on the disk, so throughput is bounded by the SSD's flush latency. Here the server calls a synchronous `fsync` per command, which blocks the event loop, so 50 clients' writes are flushed one at a time. Real Redis does *group commit*: it writes everything produced in one event-loop iteration and calls `fsync` once before sending all the replies. That is why it degrades far less in this mode.

| Mode | SET throughput | vs in-memory | p50 ms | p99 ms | Redis 7 SET |
| --- | ---: | ---: | ---: | ---: | ---: |
| in-memory (AOF off) | 64.1K ops/s | 100% | 0.391 | 2.511 | 73.5K ops/s |
| AOF, `appendfsync everysec` | 60.3K ops/s | 94% | 0.503 | 3.287 | 72.8K ops/s |
| AOF, `appendfsync always` | 1.7K ops/s | 3% | 28.911 | 54.591 | 32.4K ops/s |

## 6. Replication overhead

`SET` on a master with 0, 1 and 2 attached replicas, all on the same machine. Every write is encoded once as RESP and written to each replica's socket asynchronously. The client is not held back for replica acknowledgement unless it calls `WAIT`. The replicas also compete with the master for CPU here, so this is a pessimistic number.
